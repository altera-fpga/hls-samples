# Device Global with Host Access

This design demonstrates how to use `device_global` variables with host access to maintain state across kernel invocations, and the interfaces created by them.

## Device Global Interface

In this design, a `device_global<int>` variable `start_idx` is declared with `device_image_scope` and `host_access_write` properties:

```cpp
using DeviceGlobalProperties = decltype(oneapi_exp::properties(
  oneapi_exp::device_image_scope, oneapi_exp::host_access_write));
oneapi_exp::device_global<int, DeviceGlobalProperties> start_idx;
```

Because `start_idx` is declared with `host_access_write`, the compiler generates a dedicated Avalon memory-mapped interface on the IP component for the host to write to `start_idx`. This interface is separate from the shared CSR used by kernel invocation — it has its own `address`, `writedata`, `readdata`, `read`, and `write` signals. The host uses this interface (via `q.copy()`) to initialize `start_idx` before launching any kernels.

The kernel processes a batch of elements starting at `start_idx`, then advances `start_idx` by the batch size at the end of each invocation. Because `device_global` state is preserved across kernel invocations, the host can split the work into multiple batches without explicitly passing the current offset each time:

```cpp
for (int i = 0; i < num_batches; i++)
  q.single_task<IDSimpleVAdd>(SimpleVAddKernel{a, b, c, batch}).wait();
```

Each invocation processes `kBatchSize` elements starting from the current value of `start_idx`, then increments `start_idx` so the next invocation continues where the previous one left off. The kernel does not receive `start_idx` as an argument — it reads the value directly from the device global.

This design is meant to illustrate the IP component interface generated by a `device_global` with host access. For a more complete description of `device_global`, see the dedicated [device_global](/Tutorials/Features/experimental/device_global) code sample.

> **Note**: Because this design launches multiple kernel invocations (one per batch, waiting for each to complete), it is slower than the other examples in this sample, which process all elements in a single invocation.
